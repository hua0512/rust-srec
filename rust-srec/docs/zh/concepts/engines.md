# 引擎 (Engines)

下载器是应用程序的核心。它们负责从源头下载视频流。该应用程序支持三种下载器：`Mesio`、`FFMPEG` 和 `Streamlink`。每个下载器都有其独特的功能和局限性。

`Streamlink` 出现在两个相互独立的维度上，二者的名称很容易混淆。作为**下载器**，它是真正写出录像的进程，通过 `download_engine` 选择，也就是本页所介绍的内容；作为**提取器**，它负责在任何下载器运行之前解析出流地址，通过 `extractor` 选择，参见[引擎与提取器选择](./configuration.md#引擎与提取器选择)。两者可以各自单独设置。

> [!TIP]
> 对于 **Mesio** 用户，我们 **强烈建议** 启用 **FLV 一致性修复** 和 **HLS 一致性修复**。这两条流水线会修正或隔离时间戳与流结构变化，降低一次异常转换导致后续录制无法解码的概率。源站从未交付的媒体数据无法恢复。

`FFMPEG` 下载器是以兼容性为重点的外部引擎。它使用 C 语言编写，可下载 FLV 和 HLS 流，包括 FLV/RTMP 容器中的非标准 HEVC，但不支持多线程 HLS 下载。全新安装默认选择内置 Mesio 引擎实例；只有需要其封装或编解码兼容性时才应显式选择 FFmpeg。

> [!NOTE]
> 我们 Docker 镜像中提供的 FFMPEG 版本是来自 [yt-dlp/FFmpeg-Builds](https://github.com/yt-dlp/FFmpeg-Builds/) 的专用构建版本。该版本针对流媒体进行了优化，包含（或已合并入上游）了许多确保与 `yt-dlp` 顺畅集成的关键补丁，例如修复 AAC HLS 流截断问题、支持 Windows 长路径以及解码 FLV 容器中的非标准 HEVC。

### 录制文件名与状态跟踪

录制模板会展开配置中的日期标记，而主播名称和标题中的百分号保持字面含义。
例如，标题 `Top 5%d` 仍为 `Top 5%d`，不会替换成当月日期。启动时的输出根探测
使用相同的元数据字面值规则。

FFmpeg 录制与 Streamlink 重封装需要 info 级别日志和统计信息来跟踪分片及进度。
后端在最后提供 `-loglevel info -stats` 参数，因此自定义静默日志参数和 `-nostats`
不会关闭这些必要信息。

### 可执行文件检查

FFmpeg 和 Streamlink 的版本检查限时三秒，必要时随后执行有时间上限的进程清理。引擎测试和自定义引擎解析会异步执行检查。无法启动或未在期限内完成版本探测的可执行文件会报告为不可用。同步启动初始化也会等待同样的有界检查。

不存在的命名引擎配置保留默认引擎回退行为。数据库访问失败、已保存配置损坏及无效覆盖会导致解析失败，不再静默改变实际使用的配置。

### 停止 Streamlink 录制

停止 Streamlink 录制时，标准输出转发和标准错误读取会继续运行，直到源进程
停止。Unix 向 Streamlink 发送 SIGTERM；隐藏运行的 Windows 进程没有受支持的
控制台信号通道，因此先限时等待源进程自然退出，再强制终止。源进程最多等待
三秒，且不超过配置的剩余停止时间。随后 FFmpeg 使用同一截止时间的剩余预算，
读取管道 EOF 并完成文件收尾。

两个进程都受进程树约束。超过截止时间会强制终止进程树，直接父进程退出时也会
终止其后代。该约束假定后代进程不会主动逃离进程组或 Windows Job Object。

在 macOS 上，进程组终止请求若与主进程退出发生竞争，清理会利用强制清理预算的
剩余时间确认主进程已退出，再重试进程组终止。这不会增加新的宽限期；截止时间内
无法确认清理完成时仍会返回错误。

这会在可用时间内继续转发已经写入标准输出的数据，但不能保证保留 Streamlink
内部环形缓冲区中所有已抓取字节。上游信号处理会中断输出循环，并没有提供排空
全部缓冲数据的操作，参见[上游清理循环](https://github.com/streamlink/streamlink/blob/16fff079ca6044cbe0fd0e855720cf8fed602de6/src/streamlink_cli/streamrunner.py#L100)。强制终止仍可能截断录像尾部。

## 2. FLV 一致性修复

启用后，FLV 数据会在进入写入器前通过一条有序修复链。该链保留媒体载荷，主要修复容器层结构：

| 问题 | 流水线行为 |
| --- | --- |
| 缺少 FLV 文件头 | 在首个标签前插入有效文件头 |
| 视频或音频格式变化 | 开始写入新文件，并补充播放所需的文件头 |
| 视频数据乱序 | 在保持内存有界的前提下重排相邻标签 |
| 时间戳跳变或回退 | 调整时间戳以保持播放连续性 |
| 重复媒体标签或序列头 | 启用对应选项时过滤 |
| 达到文件大小或时长限制 | 视频在关键帧边界轮换，仅音频输出则在下一个标签轮换 |
| FLV 统计与快速定位索引 | 在文件关闭前更新元数据 |

元数据更新不会重写已经完成的媒体数据。如果可用元数据空间不足，会缩短可选的快速定位索引。带过滤或加密标记的脚本载荷保持不变。

## 3. 原始数据模式 (Raw Data Mode)

原始数据模式是 **Mesio** 引擎支持的一种高性能下载模式。在该模式下，引擎会将从网络接收到的流数据直接写入磁盘，而不对内部媒体包（头信息、帧、元数据）进行解析或处理。

### 主要特点：
- **极致性能**：由于不进行包解析或重采样（Re-muxing），CPU 和内存占用被降至绝对最低。
- **零开销**：非常适合高带宽流或资源受限的环境（如入门级 NAS 或 VPS）。仅在网络稳定且 CDN / 流来源没有数据波动（如媒体头部信息变更）时推荐使用。

### 局限性：
由于不检查包结构，启用原始数据模式时，以下高级功能将无法使用：
- **数据统计**：无法实时计算录制时长和下载码率统计。
- **自动分段**：引擎无法检测帧边沿或时长，因此无法按大小或时长进行精确分段。
- **修复功能**：无法应用 FLV 一致性修复或 HLS 一致性修复，因为这些功能需要包级别的操作。

## 4. HLS 一致性修复 (Mesio 独占)

Mesio 的 HLS 下载反应堆与 HLS 修复流水线职责不同：

- **下载引擎**负责对已抓取分段排序，先写入 fMP4 媒体所需的初始化数据，应用已配置的缺口策略，并保留播放列表不连续所形成的输出边界。
- **一致性修复**会在已交付分段出现不兼容的编解码器、分辨率、节目布局或 fMP4 初始化数据变化时开始写入新文件，并执行文件大小与时长限制。

该流水线不会改写 TS 或 fMP4 载荷内的时间戳，不能重建缺失媒体，也不会转码。被跳过的分段仍然是可观测的缺口；流水线会保持已交付输出的顺序，并在检测到需要新文件的格式变化时轮换输出。

## 5. Mesio 架构

Mesio 是**进程内的 Rust 引擎**，采用基于反应堆的 HLS 下载器，并由 HLS 与 FLV 共用统一的下载会话模型。架构图与内部工作原理详解请参阅专门的 [Mesio 引擎](./mesio.md) 页面。
